<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Relay envelope to trusted invitation store | Untrusted relay data crosses followed-sender and payload validation before it may become an actionable invite. |
| Live invite capability to durable browser storage | Capability-bearing URLs must remain in memory while only safe notification metadata and resolution IDs cross into persistence. |
| In-app feed to browser Notification API | Durable events may project to an operating-system surface only after explicit permission and category/cadence gates. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-18-01 | Spoofing | `NostrSocialStore.receiveInvite` | high | mitigate | Preserve followed-sender, decoded-payload, and resolved-ID checks before recording any actionable invitation. |
| T-18-02 | Information Disclosure | notification persistence | critical | mitigate | Serialize an allowlisted safe schema and test that URLs, tokens, raw envelopes, profiles, message bodies, and decrypted content never appear. |
| T-18-03 | Tampering | invitation resolution ledger | high | mitigate | Store stable invitation ID plus timestamp, write resolution before live removal, and prune only by the fixed seven-day rule. |
| T-18-04 | Denial of Service | feed and desktop queues | medium | mitigate | Upsert by category/key, cap non-actionable history at 100, preserve one cadence timer, and protect unresolved invitations from eviction. |
| T-18-05 | Repudiation | read versus invitation resolution | medium | mitigate | Maintain independent read and resolution records with unit coverage proving one cannot mutate the other. |
</threat_model>
